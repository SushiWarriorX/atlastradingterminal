# ATLAS contributor rules

## Never
- Add anything that places an order, links a brokerage or says "buy". Research and paper only.
- Invent or fill in data. A missing number is shown as unavailable with a reason.
- Commit secrets, keys, the SEC contact address or anyone's account email.
- Use paid APIs or sources that need an account.
- Merge, force-push, or push to a branch you were not given. Keep pull requests as drafts.

## Every figure shows
Source, as-of date, and freshness (live, delayed, stale, historical, demo). Demo data is labelled and never mixed with live data.

## Adding a data source
1. Fetch it live in the same session. Keep one trimmed real response as the test fixture.
2. If it cannot be reached, log it as blocked in `DATA_SOURCES.md`; do not ship it.
3. Timeout on every request, short cache, and a labelled "unavailable" result when it fails, with the reason worded by `fail_reason(e)` (`atlas_api/failreason.py`: plain words, no library names, no addresses, and every ISO date of a failed check in words: "September 2026", "November 23, 2026"). Never print the raw exception: a bare "(ConnectError: )" reached the screen once, and a test now guards it.
4. Test the failure, stale and demo paths as well as the good path.
5. A host that refuses the plain client (an HTTP 403, or a refusal from the network proxy) is BLOCKED for automation. Never change the client's identity, add browser-style headers, or fetch through another tool to get around a refusal: log it in `DATA_SOURCES.md` and let the owner decide. (FRED is the opposite case: send it no custom User-Agent, it stalls on one.)
6. Read the series page's own two lines before wording the card, not after. The **frequency line** says what a date means ("Weekly, Ending Monday" means the figure is the Monday one, so the card says "Monday <date>", never "week starting"; a first draft of the gasoline card got this wrong and a test now pins the right wording). The **licence line** says whether it may be shown ("Public Domain: Citation Requested" ships with the source named and the series page linked; "Copyrighted: Citation Required" ships only with the owner's say-so and the citation; "Pre-Approval Required" does not ship at all, because only the owner of the data can approve it). The page-wide banner "Data in this graph are copyrighted" is on every series and means nothing alone. The exact lines for every series so far are in `DATA_SOURCES.md` (HELD).
7. A live card may be unavailable in any one browser run. Use `liveCard` (not `present`) around its content checks in `mobile/e2e/signal.e2e.cjs`, so the run prints which cards were skipped instead of passing in silence. Check a card's wording with `match` / `noMatch` (from `mobile/e2e/soft.cjs`), not `assert` or `eq`: inside the Macro test a failed `match` / `noMatch` is collected and the test fails once naming every wrong sentence, so one changed card hides none of the cards after it, while `assert`, `eq` and a missing element end the test at once.
8. Set the self-check limits from the whole real history before writing any test, not from the window you fetch: note the true extremes, the largest one-day moves and the longest gaps, and leave margin. A series with real spikes (Henry Hub gas has jumped 4.19 times in one day) must not get a tight one-day cap, because a card that goes dark in every real event is useless. Use a loose cap that only catches x10 and /10 slips, and add a cross-check against a second series that would disagree if the first were wrong (a published monthly average, a related price). Pin one real spike with a test so nobody tightens it later.
9. Test one check at a time. Build synthetic data where every other check holds by construction (a flat series whose monthly figure is its exact average), then break one thing. When two checks overlap, the test for the second must give the first no way to mask it: the "this month never counts" rule was hidden by the 15-prices rule until a test ended the series later in the month. Only the breakage run (change one constant or one comparison, expect a failing test) finds this, so do it for every new provider. If a check can never be the one that fires because another check always fires first (the monthly range checks on bank reserves sat behind the weekly ranges, the identity and the weekly comparison), no test can prove it, so remove it and say so in the source's notes instead of keeping unverified code.
10. Say what a reading means in days, not as a "range": "in the middle of the past year's range" beside "low 2.42, high 30.72" reads as halfway between the two prices when it means half of the days were at or below. The natural gas card says "50% of its 248 days were at or below this price"; the older cards still use the shorter wording (backlog in `LOOP.md`).
11. Run every breakage script with `PYTHONDONTWRITEBYTECODE=1` and clear `__pycache__` first. Python reuses a compiled `.pyc` when the source file has the same size and the same modification second, and a one-character change (`>=` to `>`) keeps the size, so a stale `.pyc` can make a broken file look healthy (or the reverse) and a breakage count means nothing. This happened: an earlier count was re-run clean, and the clean run found one count wrong (see the 2026-11-15 correction in `IMPROVEMENT_LOG.md`). Make each "text to break" unique in the file (`CUR_MOVE = (...)` also matched inside `WEEK_CUR_MOVE = (...)`, so four breakages were silently skipped until the match was anchored to the line start). A skipped breakage is not a caught one. A breakage that survives is either a missing test or an equivalent change that cannot alter behaviour (`re.match` already anchors at the start, so removing `^` changes nothing); say which, and remove the equivalent ones from the list instead of counting them.
12. Before relying on an exact built-in check (a total that equals the sum of its parts), read the notes of EVERY part on its source page, not only the licence line, and ask whether any part is calculated from the others. FRED's two-to-four-unit housing starts (`HOUST2F`) is the total minus the other two, calculated by a third party (Haver Analytics, with its own copyright notice), so "total = parts" held in all 813 real months by construction and proved nothing (found 2026-11-17; the queue had called it an exact check). A part that is derived from the others cannot check them, and a series with a third-party copyright notice is HELD (`DATA_SOURCES.md`), not shipped. The retail sales identity is real: all three of its series are Census figures.
13. A series with "no exact identity" can still have a property that must hold, and it is worth looking for one (found 2026-11-17: the queue called industrial production a weighted aggregate with nothing to check against). An index built as a weighted average of groups moves each period between its groups' moves, so the total's one-month change must lie between the lowest and the highest group change. Measure on the whole history which series satisfy it (the SIC manufacturing series did in all 665 months since May 1971, the NAICS one failed in four, so the test also chose the right series), set the tolerance from the clean period only (76 months before 1971 break it, by up to 0.66 points), and apply it to the recent window. Say on the card which checks are exact and which are properties, and never present a check that holds by construction as evidence.
14. Read the source's own metadata and check it, and say which checks are the source's own arithmetic (found 2026-11-17, the euro-area money supply). The ECB's CSV labels every series with its unit and unit multiplier (euro in millions; percent change) and every observation with a status (provisional or not): the provider refuses a series whose labels changed, which catches a unit slip that a range check can miss (a growth rate 100 times too small passes a range of -5% to +20%), and shows "provisional" on the card. All four sums of M1, M2 and M3 hold to the million euro in every month since 1980 because the ECB builds the aggregates from the parts: that is a check that the series fetched belong to one release, not that they are right, and the card says so; the independent check is the published growth (from an index of notional stocks) against the growth of the amounts, with a tolerance set from the whole history (countries joining the euro area move the two apart by up to 3.2 points) and so loose by necessity. A comparison of a rounded maximum with an unrounded candidate lets a later tie win; keep the unrounded number and round only for output (a tie test found it). Euro-area GDP, 2026-11-18: the ECB's `csvdata` also carries `DATA_COMP` (the formula of a series the ECB calculates, for example `PCT(<level>)`) and `COMPILING_ORG` (4D0 Eurostat's own levels, 4F0 the ECB's calculations): read them before calling an identity a check, because a growth rate calculated from its level agrees with it by construction (it proves the unit and the alignment of the quarters, nothing more), while nominal GDP against domestic demand plus exports minus imports is a check between series compiled separately.
15. A test that reads its limits back from the module cannot notice a changed limit (found 2026-11-17, the euro-area consumer prices breakage run: of 204 deliberate changes 62 were first missed, and 46 of those were bounds moved in the module while the test took its bound from the module, so test and code moved together). Write the limits as literals in the test, test each side of every limit (inside it the check must pass or a later check must be the one that speaks, outside it the message names the limit), and add one test that pins the module's constants to the literals. A change from `<=` to `<` exactly at a tolerance cannot be killed in floating point (no value lands exactly on 0.05): probe 0.01 inside and 0.01 outside and list those mutants as equivalent in the log instead of forcing a test. Two more lessons from the euro-area unemployment breakage run (found 2026-11-17): a negative assertion ("the message does not say X") passes whatever happens when its pattern never matches the real message (the range-edge test looked for "%, outside" while the message read "% in 2026-09, outside", so two comparisons changed from `<=` to `<` went unnoticed), so run the pattern against a real refusal once before trusting it; and a comparison exactly at a bound CAN be tested when the numbers are exact in binary (a flat 10.0 and a step of exactly 1.0, or 0.5 and 1.5), which closed the two rate-move edges, while percent changes and a tolerance such as 0.2 cannot be hit exactly (so choose the tolerance itself exact in binary: 2 ** -6 instead of 0.01 gave the euro-area GDP check a world with a gap of exactly the tolerance, found 2026-11-18). Two more from the euro-area GDP breakage run (2026-11-18): a test that fixes the clock (`now`) must also use a second `now` that differs from the machine's date, or a provider that reads `datetime.now()` instead of the date it was given survives (it did, because the sandbox date equalled the test date); and a rounding to two decimals is only tested by a figure whose one-, two- and three-decimal forms differ (the real year-on-year growth 1.2973, net trade 147.8002 and exports contribution 1.696 all print the same at one and two decimals), so a synthetic world with chosen decimals is needed beside the real fixture (a search over simple numbers found no pair giving exactly 15% or -10%). A rounding test needs a world whose figures really differ between one and two decimals and whose changes over 1, 2, 3, 11, 12 and 13 months all differ after rounding, and should assert that about its own world, or a change of one decimal or of the span goes unseen (three months-back and two rounding changes survived because the first world's drift rounded to the same numbers).
16. List the whole dataset before choosing a key (found 2026-11-17, the euro-area stress index). One request for the latest value of every series of a dataflow (`.../service/data/<flow>?lastNObservations=1&format=csvdata`: 60 series for CISS, 3 seconds) showed what a key written from memory could not: the ECB keeps the old stress index (keys ending `SS_CI`, last value 2025-05-02) beside the new one (`SS_CIN`, current), so a stale predecessor can be fetched without any error; and it showed the six contribution series whose sum is the index, which gave the card a real identity (the gap is at most 3.3e-16 in 7,272 days) and gave the ranges and signs of the parts a set of properties (never negative, never positive). Compare the last dates of look-alike series before choosing a key, and read the components a dataset publishes before deciding that a composite has nothing to check against. A row with no value and status M is a missing value: leave it out, never read it as zero. A synthetic world of weekdays has fewer days than a real daily series (2,608 against 2,616 in the same ten years): count any literal that a test pins by hand, outside the module. Confirmed 2026-11-18 (euro-area GDP): the first key guessed from memory (`I9`, the 20-country euro area) answered without an error and ended at 2026-Q1, while the current 21-country code `I10` runs to 2026-Q3, so list every look-alike code of a composite area (`.../service/data/<flow>/<key with the area left empty>?lastNObservations=1&format=csvdata`) and compare their last dates before choosing one.
17. A check over a window turns one bad day into a window of unavailable days (found 2026-11-18, the euro-area yield curve). The ECB's published spot rates equal its own Svensson curve of the published parameters to 1.5e-10 on 5,670 of 5,675 days, so the first idea was to check that over the last 520 days, as for the spreads. The whole record shows five days where it does not hold: four in May 2007 (off by up to 6e-5) and 2022-06-23 (off by 0.056 points; that day's parameters carry 8 decimals instead of 15 and cannot reproduce their own rates). If such a day arrived tomorrow, a 520-day check would hide the card for about two years because of one blemish the ECB may never repair. So before choosing how far back a check reaches, run it over the whole record and list every day it fails: an identity that is exact on every day can reach back (the three spreads: at most 1e-10 on all 5,675 days, checked over 520), one that has exceptions is checked on the newest day only, and the card says which days each check covers. A second lesson from the same breakage run: the 2 of 238 deliberate changes that went unseen were in what the module REPORTS, not in what it refuses (a largest gap that lost its sign when a spread lay below its identity; the parameters of an older day, if the source ever sent more than one), so test every reported number with a case on each side of zero and with extra older days in the input.
18. Two lessons from the euro-area bank lending card (2026-11-18). (a) A published growth rate can often be rebuilt from the other data types of its own series family, and then it is a check between three series that carry the same units, months and pairing: the ECB's annual growth in the BSI dataflow equals the product over twelve months of one plus each month's flow over the previous month's amount, minus one (largest gap 0.0235 points over 1,071 series-months; tolerance 2 to the power -4), and the totals equal their parts to the million euro. Both are the source's own arithmetic, so they prove the units and the alignment of months, not the figures. When a dataflow's parts start in different years (household purposes in 2014, firms' maturities in 2022 here), the window of every check is the shortest history, said on the card. (b) A test that cannot fail has slipped into assertions several times (`or True`, `if False else True`, `[:0]`): in the euro-area GDP and bank lending tests when they were first written, caught by reading them before the breakage run, and in two older test files, where an assertion had never been made. `tests/test_test_hygiene.py` now refuses those patterns in every test file; read a new test file once for anything it would pass whatever happened, before spending a breakage run on it. The ECB portal answers the same key in 0.1 s to 23 s, so its providers wait 45 s and the phone 60 s.
19. Three lessons from the euro-area bank interest rates card (2026-11-18). (a) A rate that is an average has an identity with the volumes of its parts: the ECB's rate on all new business equals the average of the rates of its two parts (floating or up to one year fixed, and over one year fixed) weighted by their new business volumes, to 0.0093 points in all 285 months for each of six kinds of business, and the volumes add up to 0.010 million euro (MIR dataflow; the two-decimal rounding of the published figures accounts for both). Look for the volume series beside any rate series, take the weights from the PARTS and not from the total, and set the tolerance at the arithmetic bound of the rounding (two roundings of 0.005 make 0.01; 2 to the power -6 = 0.015625 is above it and exact in binary, so a gap of exactly the tolerance can be tested). (b) The shared failure wording `fail_reason` clips a data-check message to 110 characters, so a long series name can hide the number that failed: put the name and the figure first, keep names short, and in tests build the expected visible reason with `fail_reason(ValueError(message))` instead of typing it again. (c) The whole euro-area slice of a big dataflow can be too large for one listing (MIR: no answer in 120 seconds); list it by narrowing the key (counterpart sector and data type gave 101, 44, 97 and 34 series in 5 to 13 seconds) and compare the last dates slice by slice. A composite the ECB calculates itself with moving-average weights (its cost of borrowing) has no identity: bound it against the plain rate of the same borrowers (the gap was -0.11 to +0.48 points in the whole record), keep that bound loose, and say on the card that it has no identity of its own. (d) Time a source COLD before choosing its timeout: the ECB caches what it has just computed, so a request repeated within minutes answers in 0.1 to 0.9 s and hides the real latency. The MIR dataflow answered its four keys in 7 to 14 s while they were warm from the analysis requests, then in 10 to 49 s with an unusual `lastNObservations` (122, 123), once in 84 s and 73 s, and once not within 120 s; the first browser run to find them cold timed out at 45 s ("the request timed out" on the card, and `liveCard` listed it as not checked, as designed). Its provider waits 90 s, the phone 100 s and the browser check 110 s. Ask once with a count nobody asked for before fixing a timeout; and remember that `macro_refresh` has 180 s for every macro source one after the other, so one slow source can starve the sources after it in that run (the next run, 15 minutes later, finishes them).
20. Three lessons from the euro-area employment card (2026-11-18). (a) Test a "between the parts" property on the whole record before choosing a source for it: the CISS sovereign-stress aggregates for the euro area (`SOV_EWN`, `SOV_GDPWN`) are never above the highest of the 11 country series in 7,010 days but lie BELOW the lowest country on 1,012 and 820 of them, because the CISS method weights by the correlation between countries (a portfolio-style sum, not an average), so only an upper bound holds and the source was passed over for one with exact identities. (b) Two breakdowns that Eurostat compiles separately (the ten activities, and employees plus the self-employed) each add up to total employment, for persons and for hours, to floating-point noise (at most 8.1e-10 thousand persons and 1.3e-7 thousand hours in 126 quarters): tolerances 2 to the power -20 and -12, exact in binary, and the checks reach back over the whole window because the identity has no exception (rule 17). (c) When one series is a quarter ahead of its breakdown and every request asks for the same number of observations, the oldest quarter of one has no partner in the other (persons: 44 of 45 quarters can be compared; the oldest quarter of productivity per hour has no real GDP): compare only the quarters both have, report how many were compared (`persons_quarters_checked`), skip a quarter older than the other series' window but refuse one missing inside it, and run the provider on the real response early, because a synthetic world built from the same assumption agrees with the code that shares it (here the synthetic world had the same shape). A level printed with `:,.0f` shows 99,999.5 as 100,000 beside a limit of 100,000: print one decimal.
21. Three lessons from the US job openings card (2026-11-18). (a) A FRED download with several ids and ONE `cosd` applies the date to the FIRST series only and gives every other series in full, with no error (141 months of one series and 310 of eleven others in one file): ask for one series per request, as the other FRED cards do, and test that no id carries a comma; compare two downloads over the union of their months, not over the months both have (my first comparison said "0 differences" because the shorter one was cut). (b) Work out each rate's denominator on the whole record before fixing a tolerance: the JOLTS openings rate is openings over payroll employment PLUS openings (payrolls alone are wrong by up to 0.63 points), the other five rates are over payrolls; a published rate has one decimal, so the arithmetic bound is 0.05 plus the rounding of the level and of payrolls (under 0.001), the real largest gap over 1,860 comparisons is 0.0504, and the tolerance is 2 to the power -4, exact in binary (rule 19a). (c) A real hole inside the window (the household survey was not taken in October 2025, a shutdown) must not refuse a card that needs that series only for an extra figure: use the newest month both series have, name its month, give a year-earlier value of None when that month has none, and refuse only when no month in the window has both. A property that cannot hold on a real record is not checked and the card says so (hires minus separations is not the change in payroll employment: median gap 33 thousand, largest 12,967 thousand).
22. Three lessons from the US jobs report card (2026-11-18). (a) Measure each source's own rounding on its whole record before copying a tolerance from another: the JOLTS rates exceeded half a unit of their decimal (0.0504 against 0.05: BLS computes them from unrounded levels) while the household survey's rates never do (0.04998: computed from the published levels), and a sum that BLS publishes as a sum is exactly 0 (payrolls, 1,054 months) where three rounded values differ by at most 1; the same exact-in-binary tolerances (2 to the power -4 and 1.5) serve both, but the log must say which gap is rounding and which is exact. (b) A real hole in the record bites once, when the newest month is exactly a year after it: all seven household series have no value for 2025-10, so the year-earlier comparison of 2026-10 had nothing to compare with; a card that compares with a year ago must carry the comparison as null, say which month is missing by name (derived from the data, not asserted), count the holes in its window and refuse when there are more than the real record has (3 against 1), and the fixture must end exactly there to test it. (c) Two edges of a range cannot be reached by a consistent world when other limits bound the same quantity (total payrolls at 250,000 needs parts of at most 240,000): test that the value passes its own range and fails the sum instead, so that the range limit is still pinned by a mutation of it.
23. Three lessons from the US GDP card (2026-11-18). (a) Read an id's frequency and first dates before building on it: FRED's `PCE` is the MONTHLY consumer spending (813 months), the quarterly series of the GDP release is `PCEC`, and the quarterly-sounding id from memory (`DPCERC1Q027SBEA`) answered HTTP 404; the "same quarters" check would have refused the monthly one at once, so it stays and names the series. (b) Work the arithmetic bound of a tolerance from the published decimals of EVERY term before choosing the binary-exact number: GDP against its four parts is 5 x 0.0005 = 0.0025 (real 0.002, tolerance 2 to the power -8), net exports against exports minus imports is 3 x 0.0005 = 0.0015 (real 0.001, 2 to the power -9), and real growth against its four contributions is 0.05 for the total's one decimal plus 4 x 0.005 for their two = 0.07, which IS the largest real gap, so 2 to the power -4 = 0.0625 would have refused the real record and the tolerance is 9/128 = 0.0703125. A message that prints a tolerance with `:g` prints 0.001953125 as 0.00195312: the tests pin the printed text. (c) Boundary worlds need a helper that keeps every identity exact (net exports from exports minus imports, GDP from its parts), so that one range edge can be tested alone, and the expected gap of an off-by-one test is worked from the change, not from the headline numbers: GDP up 1.0 with net exports up 0.5 is a gap of 0.5, and a net exports gap needs exports changed, not GDP (two of my first tests expected 1.5 and 1.0 and the module was right).
24. Three lessons from the US household income and saving card (2026-11-19). (a) The ids of a series family are not the account codes printed on its series pages: the pages say "BEA Account Code: DDURRC" and the ids made from such a code (`DDURRC1Q027SBEA`, and the two like it for nondurable goods and services, and `A067RC1`, `A071RC1`, `B070RC1`, `A074RC1`) answer HTTP 404, while the real ids are `PCDG`, `PCND` and `PCESV` (monthly-looking names for QUARTERLY data; `PCE` is monthly) and `DSPI` and `PMSAVE` (monthly, 813 months from 1959-01, beside `PI`, `W055RC1`, `A068RC1`, `B069RC1` and `PSAVERT`); fetch every id before building on it and read its frequency and first date. (b) A derived series can be used when its note has been read and the card says so: the note of `PSAVERT` says saving is calculated from income, outlays and taxes and the rate from saving and disposable income, so the three sums hold by construction (largest gap 0.1 in 813 months: three values rounded to a tenth) and show only that the series belong to one release. The one check that is not by construction compares two tables of the same Bureau (the GDP release's quarterly consumer spending against the average of the Personal Income and Outlays release's three monthly figures: 271 quarters, largest gap 0.0457 against a rounding bound of 0.0505); a comparison like that must skip, and count, a quarter whose months are not all published (an advance GDP estimate comes before the last month's personal income). (c) The age at which the newest month turns OVERDUE is the release lag PLUS the time to the next release, not the lag alone: BEA releases a month 55 to 61 days after its 1st and it stays the newest until the next release about 30 days later, so 85 to 91 days is normal; the first draft said 75 and the first run on the real data (79 days) marked the card overdue on the day it was built. Work the threshold from two consecutive release dates (29 October and 25 November here). A rate computed from levels has an arithmetic bound that depends on the level (0.05 for its decimal plus 100 x 0.05 / disposable income: 0.0658 in 1959 against 0.0507 since 2000), so a check that reaches back over the whole record needs the older bound (9/128, not 2 to the power -4).
25. Three lessons from the US job openings by industry card (2026-11-19). (a) Count how many parts of an identity a source really carries before promising the identity: of the Bureau's industry series FRED has 16 (its ids are the industry code with the trailing zeros cut, `JTS1000JOL`, or six digits when the code ends in 99, `JTS540099JOL`; the ids for mining and logging, information, financial activities, other services, wholesale trade, transportation, private education and the federal government answered HTTP 404 in every form tried), so the queue's question whether the private industries add up to total private could not be tested, while three smaller sums hold to the thousand in all 310 months (total nonfarm = private + government, manufacturing = durable + nondurable goods, leisure and hospitality = arts + accommodation and food): probe the ids and list which exist before writing a queue note. (b) A figure worked out by subtraction from a classification's known structure (the federal government, private educational services, wholesale trade with transportation and utilities, and four private industries together) is shown as a row only if the API marks it `derived`, the card says "by subtraction" and its only check is a floor (a part never above its whole by more than the rounding), because nothing can check it; the structure itself was written from memory (the release table is loaded by script and cannot be read here), so the sums that hold in all 310 months are its only support, and the card says so. (c) The arithmetic bound grows with the number of rounded terms, here in thousands: two values 1.0, three 1.5, seven 3.5, each exact in binary, so a gap of exactly the tolerance can be tested. The first breakage run of this provider (357 changes, 349 caught) found three kinds of gap that a first test file of 191 passing tests does not show: a list sorted by size needs tie tests in which the order of the table, the alphabetical order of the labels and the alphabetical order of the keys DISAGREE (the first ties agreed in all three, so a sort on the keys instead of the labels survived; one tie of education and health with business services and trade closed it, one of health care with private education closed the other); the oldest and the newest pair of months need a skip of their own (`zip(months[1:], months[2:])` left the first pair out and no test missed a month right after the oldest one); and a reported number kept to three decimals needs a value whose two- and three-decimal forms differ and are exact in binary (2.125 and 799.875).
26. Three lessons from the dealers card (2026-11-24). (a) A self-check that compares two series of the SAME source can fail on live data without any fault in our code, because the source revises its old weeks and does not always revise both series by the same amount: between the saved downloads of 2026-11-10 and 2026-11-24 the New York Fed moved ONE level, 2026-10-21, from 425,643 to 411,822 million (-13,821), moved that week's change figure only from -17,855 to -17,132 (+723) and the next week's change figure from 27,116 to 40,937 (+13,821, the level's move), so for that one week the levels give -31,676 and the change figure says -17,132 while every other week of the 26 still fits. When a live check goes red, compare the SAVED earlier response with a fresh one row by row before touching anything (a three-line script showed it at once), save the fresh response as a second fixture (`tests/fixtures/nyfed_pd_treasury_20261124.json`), and decide in writing what the check is for: here the red alarm stays for the week the card SHOWS (the latest week must equal the source's own change figure) and an older week the source no longer fits with itself is named in neutral words with both figures and the plain sentence that the card cannot tell which is right; the three-way rule (match, latest week fits, latest week does not fit or the server is older and says nothing) lives in `mobile/src/lib/dealers.ts` so a unit test covers it. Never loosen the tolerance or drop the week to get green. (b) In the browser suite `match` and `noMatch` THROW, so the first failed check in the long Macro test ends that whole test: every card after it (here futures positioning and about thirty more) was NOT looked at, and the footer line "Every live card had data..." still printed, which read as if they had been. When the Macro test fails, find which card stopped it (the log names the assertion), and run the rest in a scratch copy with that block taken out (delete the copy afterwards, never commit it) before saying the later cards are fine; LOOP.md has a backlog item to make each card's checks independent. (c) A test that sets the process timezone shows what a date helper really does: `dayText` builds `T12:00:00Z` and formats in UTC, and a test with `TZ` set to a zone 14 hours ahead of UTC and one 11 hours behind catches the removal of the `timeZone: "UTC"` option, which a test run on a UTC machine can never see (set `process.env.TZ` inside the test and put it back in `finally`).
27. Three lessons from the euro stock rates card (2026-11-24). (a) Group a dataflow slice's series by data-type code and title BEFORE deciding what it can check: the queue asked whether the ECB's rates on outstanding amounts have an identity with the stock volumes of the BSI cards; one request (`M.U2.B......EUR.O`, 253 series in 1.4 s) showed that the slice has no volumes at all and that it carries instead the ECB's own decomposition of every rate's monthly change into a rate part and a weight part, with running totals since 2003 (a Bennet index), which is an identity inside one release and holds to 0.01 in all 285 months. (b) Test an identity on EVERY series you will use, on the whole record, not on one sample, and look at how the real gaps are spread before choosing a tolerance: it holds for the five rates used (gaps of exactly 0 or 0.01 in 1,420 monthly pairs, and in about 190,000 pairs of months) and FAILS for two siblings of the same slice (repurchase agreements by 0.58 in 2024-04, house purchase up to one year by 0.14 in 2019-09), which were left out with the reason said; figures published to two decimals leave gaps on a grid of 0.01, so a tolerance of 2 to the power -6 sits between the real 0.01 and the next possible gap 0.02, and the theoretical bound of four rounded terms (0.02) was never reached. (c) A check of each pair of months can hide a drift that adds up: a ramp of 2 to the power -7 in each of the last three months passes every monthly identity (each gap 0.0078) and leaves the rate 0.0234 away from its accumulated change over the window, which only a whole-window check sees; the tests build exactly that ramp, and a slow drift of 119 steps. Two smaller lessons: a check's message is clipped to 110 characters by `fail_reason`, so the card's own names are short ("loans to firms", "consumer and other loans") and a test pins the length of the longest message of every kind; and one sentence of the Check line lacked its verb ("the rate moved as far as the accumulated change") although every pattern of the browser test matched it, so read the sentences of a new card in the screenshot as English, not only as the pattern the test expects.
28. Three lessons from the real consumer spending card (2026-11-24). (a) A chain-type index makes an accounting identity APPROXIMATE, not exact, even when the source derives both series: real spending (chained 2017 dollars) times the PCE price index over 100 does not equal spending in the dollars of the day to the rounding of the figures. Over all 237 months the gap is up to 0.0378% of spending (5.9 billion in 2021-03, when relative prices swung), against about 0.2 billion that rounding explains, so a tolerance chosen as "rounding" would have refused the real record and one chosen without looking would have been arbitrary. Measure the gap on the whole record, name its cause in the module (the Bureau chain-weights both), and state the tolerance as a fraction of the series with its margin (2 to the power -10 = 0.0977%, 2.6 times the largest real gap and about ten times tighter than the 1.0% by which the core index differs from the headline one in the newest month, so a swapped series is caught). The series pages said the Bureau derives these figures; that does not make the identity exact. (b) A limit that is not representable in binary refuses a value exactly on it: +5% from 105 / 100 comes out as 5.000000000000004. Judge a move after rounding to four decimals and pin the rounding with tests either side of the limit (5.00004 passes, 5.00006 does not). (c) A rounded change that is a tiny negative becomes -0.0, which JSON writes as `-0.0` and a formatter may print as `-0.00%`: add 0.0 after the rounding (it turns -0.0 into 0.0) and test it with `math.copysign` and `json.dumps`; the phone helper names no direction for a figure that shows as 0.00.
29. Three lessons from the US international trade card (2026-11-24). (a) When the checks form a grid, probe every cell before choosing the source: the queue named three ids from memory (`BOPGSTB`, `BOPGEXP`, `BOPGIMP`) and described one identity, balance = exports minus imports; the probe showed that `BOPGEXP` and `BOPGIMP` are the GOODS series (the totals are `BOPTEXP` and `BOPTIMP`) and found the services series (`BOPSEXP`, `BOPSIMP`, `BOPSTB`) and the goods balance (`BOPGTB`), which turned one identity into six (three balances against their exports and imports, two totals against goods plus services, and the total balance against the goods and services balances), all exact to the rounding of the figures (an integer gap of at most 1 million in 417 months, tolerance 1.5 = three terms rounded to a million). (b) With several sums, say in which order they are checked and write the test of each so that no earlier sum speaks first: a bump of one balance also moves another sum, so the test for the total exports sum moves the total balance with it, and the sixth sum (the total balance against goods plus services) can fail alone only when the other five sit exactly at the tolerance: its gap is the sum of the others' gaps, so the test sets total exports 1.5 over, total imports 1.5 under and the total balance 3.0 over (gaps 0, 1.5, 1.5 and 3.0). Work such a test from the algebra of the gaps before writing it. (c) The default world of a test file decides which edge tests are possible: my first world (goods bought 300,000, services 100,000 and 70,000) turned a 50% fall in total imports into a surplus of 115,000, beyond the balance's own upper limit, so the on-the-limit case failed for a reason of the world and not of the module; the world was changed to a larger deficit (-200,000) and every literal that depended on it moved. Also check that a world shows what a test claims: in a world whose cycles divide twelve, a year-on-year change is exactly 0.0, which shows no rounding at all, so the guard on the rounding was moved to a figure (goods imports: 1.5, 1.54, 1.539) whose one-, two- and three-decimal forms differ.
30. Three lessons from the US hires, quits and layoffs card (2026-11-24). (a) Probe the WHOLE grid before choosing the design: one request per id with six at a time took 5.5 s for 80 ids (16 industry codes by five measures) and showed that layoffs and other separations exist only for the three totals (26 ids answer HTTP 404), so the per-industry identity the queue had planned could not be built, and that the id I had written for durable goods (`JTS3100`) was a wrong guess (it is `JTS3200`; nondurable is `JTS3400`): a 404 for an id from memory says nothing about the series, so check the code table before writing that something does not exist. (b) When sums share series, work the algebra of their gaps before writing their tests: total nonfarm = private + government (tolerance 1.5) and separations = quits + layoffs + other (tolerance 2.0) share the separations of all three totals, so a private total moved alone also breaks the nonfarm sum and the nonfarm separation sum speaks first; to reach the private sum alone the nonfarm total has to move 1.5 with it, inside both tolerances (a draft of mine that moved private and nonfarm together and expected private to speak was wrong, and so was my first guess for the closest margin, 100 where the default world gives 120). (c) A refusal that names a date used to print it as the code held it: the live gasoline card refused ("no WTI crude price near 2026-11-23": the crude price lags the weekly gasoline price by a few days) and the Macro browser test failed on a raw date on the screen. The two refusals of `gasoline.py` that name a week now write "November 23, 2026" and a test pins them; the other 19 providers whose refusals named a month as "2026-09" got the fix at the 18 UTC improve job in one place: `fail_reason` now writes the dates of every failed-check message in words, so a check may build its message with `_label(d)` or `d.isoformat()`; only a refusal sentence written outside `fail_reason` has to write its date in words itself.
31. Three lessons from the US business inventories and sales card (2026-11-24). (a) A sum that holds EXACTLY in the whole record (417 months, a gap of 0) still gets the arithmetic bound of its rounding as its tolerance (four figures each rounded to a million: 2.0), not zero and not the measured gap: a revision that moves one figure by a million is rounding, and a gap measured on the past says nothing about the next release; the exactness goes in the module's docstring and the real-record test pins the gap at 0.0. (b) A ratio the source publishes to two decimals can never match its parts exactly: its tolerance is half a hundredth plus the rounding of the figures it is worked from (0.0051, with the real largest gap at 0.004996, so the margin is 0.0001: a ratio published to one decimal would refuse the card, with a message that shows both figures). Floating point cannot put a gap exactly on 0.0051, so the edge is tested at 0.0050 (passes) and 0.0052 (refused) and the one change from `>` to `>=` is listed as equivalent in practice. (c) The 12 ids written from memory all answered, but the grid also held look-alikes (the same total not seasonally adjusted, `TOTBUSIMNSA`; sales in chained dollars, `CMRMTSPL`) and one wrong guess (HTTP 404): the units and adjustment line of each series page is what tells the series wanted from its twins.

## Changing the phone UI (found 2026-11-17: the accessibility gate)
The `a11y` scenario of `mobile/e2e/signal.e2e.cjs` (part of the default run; `node e2e/signal.e2e.cjs a11y` alone takes about 45 seconds) opens 11 screens and fails the run on any WCAG 2.x A or AA violation found by `axe-core`, on any tappable element under 44 by 44 points, and on a labelled control whose spoken name does not contain the words it shows, in order. So:
1. Make every tappable thing at least `TAP` (44, from `components/ui.tsx`) in both directions. The web build ignores `hitSlop`, so the touchable itself has to be that big; a chip keeps its drawn size inside a 44 high button. There are no exceptions: the one-line "Source: ..." link that ends a card is `<SourceLink url={link}>Source: ...</SourceLink>` from `components/ui.tsx` (a 45 point target made by 15 points of padding above and below the text that an equal negative margin takes back, so the layout does not move). Never write that link as an inline `Pressable` again. The gate also counts the card source links it measured on the Macro screen (34 on 2026-11-17); if that number is 0 the probe looked at an empty screen and its clean result means nothing.
2. Give an icon-only button an `accessibilityLabel`; build a list row's label with `spoken()` (`lib/format.ts`) from the words the row shows, in the order it shows them, and draw a round logo beside the button with `LogoSlot` so its letters are not read out. Tabs sit in a `tablist`.
3. A new screen goes into the `screens` list of the scenario. Keep the light TradingView-style look (LOOP.md rule 6) and read the screenshots: the gate does not see layout.
4. What it does not cover: a real screen reader, keyboard focus order, text scaled to 200%, and the contrast of text over a gradient (axe says how many items it could not measure).

## Dependency check (before adding a dependency, and about once a week)
- Phone: `npm audit --omit=dev` in `mobile`. Fix what is reported with `npm audit fix` (semver-compatible only), never `--force`, then run every suite. Do it in this order: `npm audit fix --dry-run` (it prints how many packages are added, removed and changed), the fix itself, then check that `package.json` did not change and that no added or changed lockfile entry has an install script or an OS/CPU limit (a Windows install cannot be tested here), then `npm ci` to prove the new lockfile installs from scratch, then every suite, then compare this run's screenshots with the previous run's pixel by pixel (the differences should be clock text only). A `--force` suggestion can be a downgrade: on 2026-11-15 it offered `expo@52.0.49` for the `expo` 58 in use, so it was declined and the three advisories behind it were recorded in `LOOP.md` instead.
- Backend: audit what a FRESH install pulls in, not this machine's Python. Copy `atlas/backend` to a temporary folder, make a new virtual environment, `pip install` the copy with its `[dev]` extra, `pip freeze` it (leave out the atlas package itself), then run `pip-audit -r <that file> --no-deps --disable-pip` from a separate environment that has `pip-audit`. The machine's global Python holds unrelated packages: auditing it on 2026-11-14 gave 85 advisories in 8 packages that ATLAS does not use, and the clean install had none.
- Say in the log which environment was audited, and what the owner's own machine might differ in (an older install keeps older versions, because the requirements are minimums).

## After an outage (found 2026-11-17)
When a session was down, the scheduled triggers queue up and arrive together (31 did, over 30 hours). Read them all, then do ONE hourly cycle for the CURRENT hour, not one per missed trigger, and say in the hand-off row how many cycles were missed. The daily btcquant run catches up by itself (it steps every account through each missed candle in order), but if the working tree holds unpushed protocol changes, run it in a throwaway `git worktree add --detach <dir> origin/feature/research-modules` so that the report and the dashboard cannot name a protocol version that is not pushed yet; commit and push from there with `git push origin HEAD:feature/research-modules`, remove the worktree, then `git pull --ff-only` in the main tree. A restart in the MIDDLE of a job is different from an outage: the working tree and the scratch folder survive, the session's plan does not (2026-11-24, 18:35 to 20:18 UTC: the 18 UTC job's code, tests and documents were edited and not committed). Look at `git status`, the task list and the newest scratch folder, finish and push that job first (its board row, hygiene tests, scan), then take the current hour's job, and write in the log and the hand-off row which hour did not run: a missed hour is not made up.
